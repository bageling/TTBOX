## 二、假功能清单（实测逐条定性）

分类约定：

- **纯桩** — 有路由，返回固定结构，无任何后端逻辑
- **未实现** — 路由存在，直接返回"待做/下沉 T2.x"
- **平台错配** — 有真实实现，但本机（RK3588）必然不可用
- **空壳** — 只有内置默认项，市场/云端侧没接

### 2.0 十二个页签的真假总账

| 页签 | 真 | 假 / 不可用 |
|------|----|------------|
| 01 总览 | 实时预览、链路延迟、采集/检测帧率、目标状态、运行摘要、启停、截取尺寸、FOV、置信度/IOU、重置、重启关机 | — |
| 02 热键控制 | 热键与类别编辑、目标类别、移动倍率、X/Y 偏移、物理按键屏蔽 | **【2026-09-18 更正】** 先前记为"4 项 PLANNED、控件禁用"是**错的**。实测这些控件**正常可编辑、可保存、接口返回成功**（如 `hotkey_guard_enabled` 在 `index.html:5423` 就是普通 `<input type="checkbox" data-config>`），值只是被 `web_body_to_profile()` **静默丢弃** ⇒ 性质是「**能填、能存、不生效**」，比"禁用"隐蔽得多。实际清单 **9 项**：`hotkey_guard_enabled`、`hotkey_guard_toggle_hotkey`、`zoom_enabled`、`zoom_toggle_hotkey`、`zoom_factor`、`toggle_offset_enabled`、`toggle_offset_hotkey`、`toggle_offset_x`、`toggle_offset_y`；另有第 10 项更严重——**`addAimProfileButton` 新增的热键卡片里，第 2 张及以后保存后消失**，因为后端只取 `aim_profiles[0]`（`ttbox-web.py:905-907`） |
| 03 移动控制 | 新面板该页只有 **95 行**（`index.html:5437-5532`），3 个子页签（PID / 拉枪曲线 / 持续提前量）、30 控件；PID、预判、跟随、死区、拉枪曲线为真 | **能填能存不生效 8 项**：`controller_ki_x`、`controller_ki_y`、`controller_selector_max_lost_frames`（字段名与后端不匹配）、`controller_aim_fire_lock_y`、`controller_y_axis_fire_hotkey`、`controller_continuous_lead_fade_in_ms`/`fade_out_ms`/`near_disable_ratio`。**另：该页被漏搬了 5 个子页签**（详见下方「重大发现」） |

### 2.1b 对 2.1 的两处实测更正（复核后修正）

前一版把这两个端点的"客户可见性"判重了，逐字回读调用点后更正：

| 端点 | 前一版结论 | 复核后 |
|------|-----------|--------|
| `/api/remote/*`（4 个） | "模型库页的'远程导入'整块无实现" | **现役控制台里根本没有"远程导入"这个 UI**：`index.html` 全文 `remote` 出现 **0 次**、`远程` 出现 **0 次**。唯一调用方是**已停用**的 `static/legacy/app.js:7682/7705/10070/10905`。⇒ 这是 **API 层死端点**，客户既看不到也不可触发（与 §3.2b 的 `api_v1.py` 同性质） |
| `/api/announcement` | "客户会看到公告区异常" | **客户看不到**。`index.html:7416-7420` 是 `try { announcement = await api(...) } catch { return; }`，而 `api()`（`index.html:7494`）在 `ok:false` 时必 throw ⇒ 被 catch 吞掉直接 return。`announcementDialog` 永不打开。⇒ 属**静默失败** |

这两条不改变"接口是桩"的定性，但改变了**优先级**：`/api/remote/*` 从"客户可见的假功能"降为
"死端点"，`/api/announcement` 同理。真正会被客户**点出来看到报错**的，是下面这几组。

### 4.2 但有三个必须处理的问题

1. **地址是 Cloudflare 免费临时隧道**（`*.trycloudflare.com`）——这类域名每次隧道重启就变，
   绝不能留在出货镜像里。
2. **`app_secret` 明文躺在客户可读位置**（`default.json` 0640 root:ttbox，ttbox 组可读；
   而 web 进程就是 ttbox 身份）⇒ 客户可读出密钥，自行伪造卡密验证/心跳请求。
3. **公告接口没有配置源**：`default.json` 里**没有任何 announcement 键**，代码里也没有默认地址
   ⇒ 这就是 `/api/announcement` 恒 503 的原因（见 2.1）。要接公告，得先有地址，再补配置项。

### 4.3 影响面

换服务器时，`license_base_url` 是单点，改配置即可；但要注意设备指纹绑定
（`DeviceFingerprint::bind_string()` 只返回 `cpu_serial`，本机 `9ecf266dc8154491`）——
按已定决策「换服务器后已激活机器作废、重新激活」，不需要迁移逻辑。

### 4.4 `app_secret` 是什么、风险有多大（P0）

它不是"密码"，是**签名密钥**。板子不把密钥发上线，而是拿它把每次请求算成一串签名：

```
X-Signature = hex(HMAC-SHA256(app_secret, canonical))
canonical   = method + "\n" + path带query + "\n" + ts + "\n" + nonce + "\n" + body原文
```

证据：`plugins/web/lib/cloud_client.py:126-131`（签名的唯一实现点）。

关键点三条：

1. **全设备共用同一把**——`X-App-Key` 固定为 `ttbox`，密钥也是同一个值。
   所以一台设备泄露 ≠ 只影响一台，而是**等于所有人的钥匙都出去了**。
2. **本机确实读得到**（板端实测）：`/opt/ttbox/config/default.json` = `640 root:ttbox`，
   `id ttbox` → `uid=998 gid=998 groups=998`，而 `ttbox-web` 进程就是 998 ⇒ 组权限放行。
3. **拿到能干什么**：为任意机器码伪造合法签名，冒充客户端调 `/api/client/card-login`、
   `/api/client/heartbeat`，或自行探测接口。

代码里对这个风险是有意识的——`cloud_client.py:35-46` 注释明写「绝不硬编码进源码」，
源码内 `DEFAULT_APP_SECRET = ''` 配 fail-closed 守卫（`:140-142`）。方向对。
但"真值只放板端配置"绕不开一个事实：**板子交出去，配置就交出去了**。

处置方向对比（第 7 条已选「加密存储」）：

| 方向 | 能防住 | 防不住 | 代价 |
|------|--------|--------|------|
| 加密存储（**已选**） | 顺手翻配置的人、明文转发、截图外泄 | 有 ttbox/root 权限且做定向分析的人、内存/磁盘取证 | 低，板内改 |
| 密钥挪给 core 代发 | 上述全部（secret 改 0600 root:root，web 读不到） | root 本人 | 中，web 侧 + 一条 IPC，服务端不动 |
| 改非对称签名 | 单台泄露可隔离、可按设备吊销 | —— | 高，服务端要改 |

根因：**解密所需的一切必须与密文同机**，这是"客户端共享密钥"这个前提带来的，换存储形式消不掉。

### 6.2 定案依据（代码级证据，供执行时对照）

- **`app_secret` 的性质**：它是 **HMAC-SHA256 签名密钥**（`plugins/web/lib/cloud_client.py:126-131`），
  `X-Signature = hex(HMAC-SHA256(app_secret, canonical))`；
  `canonical = method + "\n" + path带query + "\n" + ts + "\n" + nonce + "\n" + body原文`
  （**无末尾换行**，实测带尾换行会 401）。
  它**不随请求上线**，但**全设备共用同一值**（固定 `X-App-Key: ttbox`）。
- **板端实测**：`/opt/ttbox/config/default.json` 权限 **`640 root:ttbox`**，
  `id ttbox` → `uid=998 gid=998 groups=998`，而 `ttbox-web` 进程即该身份 ⇒ **本机可读**。
- **「键鼠盒子静默回退」精确定位**：`Application.cpp:344-368` 把
  `kmboxnet/makcu/ferrum/kmboxb` 送进统一 `OutputBackend`，但 `OutputBackend.cpp:102-109`
  只认 `usb_proxy` / `local_hid` ⇒ `configure()` 返回 false 并带 `"未知输出后端: <kind>"`，
  而 `Application.cpp:365` 仅 `TTBOX_LOG_WARN("OutputBackend 配置失败（回退 aibox）")`，
  随后 `:370-379` 落到兜底分支建 `AiboxHidOutput`（本机 `/dev/hidg0`）。
  第 8 条决定把这条链整条删除，此处记录以证明"删得掉、且删在哪"。
- **附带发现**：`cloud_client.py:52/249` 的 `/api/client/app-info` 注释标「P2 公告/强更预留」
  ⇒ **公告源本就设计在该接口上**，`/api/announcement` 恒 503 属「**未接**」而非「无设计」。
  第 3 条「补发现机制」可与此接口共用同一签名通道。

### 6.4 app_secret 加密存储的残余风险（据实记录，非否决）

第 7 条选择「加密存储」。按该方案落地时，能拦住的和拦不住的要分清：

| 能拦住 | 拦不住 |
|--------|--------|
| 顺手翻配置文件的客户/售后 | 有 `ttbox`（uid 998）或 root 权限、且愿意做定向分析的人 |
| 明文直接换台设备即用 | 在本机读取解密后的内存/文件系统 |
| 配置被随手转发、截图外泄 | 拆盘离线分析 |

根本原因：**解密所需的一切都必须与密文同机**——这是"客户端共享密钥"这个前提本身带来的，
换任何存储形式都消不掉。要真正消除，只能改非对称签名（第 7 条备选之一），代价是服务端要改。
**记在此处供后续决策，不阻塞本轮执行。**
