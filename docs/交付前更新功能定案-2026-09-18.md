### 1.3 顺带挖出的真缺陷：健康检查三处全错（此前从未执行过）

`ttbox_ota_updater.py:115-125` `default_health()` 判定式：

```python
biz_ok = bool(st.get("model_loaded")) and bool(st.get("license_available"))
```

对照真实 IPC 契约：

| 位置 | 更新器写的 | 实际应为 | 证据 |
|------|-----------|---------|------|
| 请求字段名 | `{"cmd":"GET_STATUS"}`（`:107`） | `{"type":"GET_STATUS"}` | `core/src/ipc/IpcServer.cpp:450` `request.find("type")` |
| 模型字段名 | `model_loaded` | `current_model_id` | `IpcServer.cpp:890`（`data.set("current_model_id", ...)`） |
| 授权字段名 | `license_available`（平铺） | `license.activated`（嵌套对象内） | `IpcServer.cpp:895-921` License 块 |

全仓 grep：`license_available` **只在 `scripts/ttbox_ota_updater.py:121` 出现一次**，core / web / 前端皆无此键 ⇒ 该键从来不存在。

后果：`st` 恒为 `{}`，`biz_ok` 恒假，健康检查 **100% 失败** ⇒ 升级会"装上 → 30 秒后自动回滚 → 报 `health_check_failed`"。

从未暴露的原因有二：
① 7 个单测把 `health` 作为依赖注入（`tools/ota/test_verify.py:127` `health=self.health()`），
   **真实 `default_health()` 从未被执行**；
② 更新器从未进过 payload ⇒ 板端从未运行过。

> 这条同时解释了 D03「假成功」的另一半：即便把 web 的调度修对，装完也会因健康检查恒假而自动回滚，表现为"升级永远失败"。

## 二、业主已拍板的决策（2026-09-18）

### 2.1 交付形态

| 决策 | 内容 |
|------|------|
| **保留面板更新 UI** | 不做减法下线，把"检查更新 / 安装更新 / 进度 / 日志"做通 |
| **更新方式** | 只做一条：从远程服务器拉分发包升级。**U 盘（scan-otg）不做** |
| **服务器地址** | **写死在盒子里**，指向业主自建的分发服务器；业主承诺**交付前把服务器弄好** |
| **不做** | `check` 之外的联网发现不需要（服务器即真源）；`cancel` 不做（换链是秒级原子操作）；面板"切换版本"「清理卡住状态」两个按钮删掉 |
| **自动回滚** | **保留**（`run()` ⑦b 的内置能力），这是升级线最重要的兜底 |

### 2.2 特权通道（web 非 root 怎么驱动 root 更新器）

选定：**面板写任务文件 → systemd 路径单元监听 → 拉起 root 更新器**。

约束事实：`deploy/systemd/ttbox-web.service:14-15` `User=ttbox` / `Group=ttbox`；全仓 **无 sudoers / polkit / pkexec**（四种 grep 零命中）。

选此方案的理由：面板只能往一个 0770 目录丢文件，权限面最小；不新增常驻进程；更新器保持一次性脚本形态不变；
且更新器自身强制验签 ⇒ 即便有人能触发更新，也只能装我们签过名的包。

### 2.3 健康检查判据

选定：**三个服务进程 active + 模型已加载；不看授权。**

`HEALTH_UNITS = ("ttbox-core","ttbox-web","ttbox-usbproxy")`（`:49`）保留；
`biz_ok` 改为只读 `current_model_id` 非空。

不放授权入判据的理由（记录在案）：授权是客户状态，与"本次升级是否成功"无关。
把授权放进升级门禁会造成死锁 —— 客户授权到期 ⇒ 升不了级 ⇒ 而升级可能恰恰是解决授权问题的手段。

### 2.4 版本限制

选定：**禁止降级，不留人工口子。**

- 规则：OTA 新装入的包版本必须 **高于** 当前版本，否则拒绝（新错误码 `downgrade_rejected`）。
- 例外：健康检查失败后的自动回滚 **不受此限**（那是保命路径，不是"装包"）。

### 2.5 局域网黑名单（D04）

选定：**整块下线删干净。**

理由：现状是"看起来在拦、其实全放行"（`ttbox-web.py:1432-1441` `_is_blocked()` 只读内存里的 `blocked_ips`，
而名单来源脚本 `:1847` `/opt/ttbox/scripts/lan_blocklist.sh` 未进 payload ⇒ 名单恒空 ⇒ fail-open，
且 `:1521` 仍把它当门禁用）。**坏掉的安全功能比没有更危险**，因为使用者以为被挡住了。

### 2.6 签名私钥

选定：**重新生成一对新密钥，旧的作废。**

理由：现私钥明文躺在另一仓库（`TTBOX-Module-Edition-main/tools/ota/.testkeys/`），无法证明从未外传；
而**尚未出过任何货**，换密钥代价为零。

### 2.7 随附定语（业主未逐一过问，由主理人定）

- 公钥打进发布包，落点 `deploy/keys/`，`KEYS_DIR` 改为指向该处
- 修正 ④ 的方式：**改前端**（前端改发 `{url, key_id}`），后端 `_ota_install_impl` 的完整实现不动
- D01、D02 一并修（构建目录守卫；打包失败不再吞成 exit 0）
- 出厂重置维持"不做"，仅在交付文档写明"不提供"
- 私钥永不入包（`.gitignore:177-181` 红线不变）
