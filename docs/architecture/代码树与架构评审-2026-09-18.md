## 一、结论先说

三句话讲完：

1. **架构选型没走错，分层与依赖方向基本健康。** 唯一真正的问题形态是「**架子搭了、线没接**」——抽象层建好了但生产链路仍走老路，于是同一套逻辑存在两份。
2. **该动的只有 6 处**：3 处是死代码清理（低风险、可机械完成），3 处是巨石文件拆分（中风险、必须有测试兜底）。
3. **不建议做「为了分层的重构」。** 仓内已有两次「抽象层落地但未接线」的先例（`core/src/controller/` 与 `CoreInterface` 边界链，见 §四 P1-1/P1-2）。再叠一层抽象，只会让下一任接手的人更绕。

## 四、问题清单

分级：**P0 = 事实错误/孤儿资产**；**P1 = 架构债（影响维护成本或误导后来者）**；**P2 = 卫生问题**；**P3 = 可选优化**。每条附可复核证据。

### P0 —— 孤儿与重复资产（建议先清，风险最低）

**P0-1 `game-assist-lab/` 未跟踪且全仓零引用。**
证据：只有 `core/math3d.py`、`core/memory.py` 两个文件；`grep -rl game-assist` 全仓仅命中自身；无 `__init__.py`、无 README、无测试、无 CMake/systemd/docs 引用。
补充事实：`memory.py` 是全仓**唯一**出现 Windows 专有 API（`ctypes.WinDLL("kernel32")` / `ReadProcessMemory` / `IsWow64Process`）的文件，与「aarch64 Linux 板端」不相容；`math3d.py` 是全仓**唯一**出现三维投影（`view_matrix` / `projection_matrix` / `world_to_screen` / `angle_delta`）的实现。
建议：先定性（是原型？是 Windows 侧另起链路？），再决定入库并补 `__init__.py`/README/测试，或移出仓库。**在定性之前不要动它。**

**P0-2 根 `third_party/rknn/` 与 `core/third_party/rknn/` 逐字节重复。**
证据：`cmp -s third_party/rknn/rknn_api.h core/third_party/rknn/rknn_api.h` 通过（完全相同）；`core/CMakeLists.txt:199` 取的是 `${CMAKE_CURRENT_SOURCE_DIR}/third_party/rknn`，即 `core/` 下那份 ⇒ 根副本无消费方。
建议：删根副本。`README.md` 已把它标为「待出清」，本报告只是给出可执行判据。

**P0-3 `core/include/ttbox/core/CoreInterface.hpp` 领头的「稳定边界」链整条已死。**
证据（反向引用图）：

```text
CoreInterface.hpp      ← 无人引用（0）
 └─ CoreInterfaces.hpp ← 仅被 CoreInterface.hpp 引用
     ├─ ICapture.hpp    ← 另被 capture/V4L2Capture.hpp 引用（★这条活）
     ├─ IMouse.hpp      ← 仅死链
     ├─ ICoordinate.hpp ← 仅死链
     └─ IDetector.hpp   ← 另被 rknn/Detector.hpp 引用，但 Detector.cpp 未进构建（★也是死）
```

即：曾计划的分层边界（Detector/Coordinate/Mouse 三个接口）只有接口声明、**没有任何实现**，`core/src/coordinate/` 与 `core/src/detector/` 各只有一个头文件。
建议：要么补实现把链路切过去，要么删掉死链。**留着比删掉更贵**——它会让人以为已有分层边界。

**P0-4 `core/src/auth/NullLicenseClient.hpp` 无人引用。**
证据：全 `core/` 树反向引用为 0。其文件自述用途是「在无在线授权客户端时断开 ODR-use」，该目的已在别处达成。
建议：确认后删除，或补注释说明为何必须保留。

**P0-5 两个 `.cpp` 存在但未进构建。**
证据：`core/src/bench/npu_bench.cpp`、`core/src/rknn/Detector.cpp` 在 `core/CMakeLists.txt` 中查无此名（`core/tests/{board_DecodeNMS,fp16_probe,layout_probe}.cpp` 同理，但它们是探针，`废弃代码清单.md` 已覆盖）。
建议：`bench/npu_bench.cpp` 若还要用就接进构建或移到 `tools/`；`Detector.cpp` 与 P0-3 同源，一并处置。

### P1 —— 架构债（真正影响维护）

**P1-1 同一套控制逻辑存在两份，抽象层建好但生产链没切。**
证据：

- 生产链：`core/src/aim/AimThread.cpp` 内联实现输出链（`out_sensitivity × out_scale` 在 105–108 行取值、251–292 行应用 deadzone/remainder）。
- 抽象层：`core/src/controller/PidController.{hpp,cpp}` 自述「封装 Pid1Controller + 输出链」「行为与 AimThread 现状完全一致」。
- 引用图：`PidController` 只被 `core/tests/{pipeline_bench,test_pipeline,test_real_model,test_tracker,test_win_e2e}.cpp` 与 CMake 提及；`core/src/runtime/` 与 `core/src/app/` 中 **`PidController`、`Pid1Controller`、`IController` 三个名字一次都没出现**。
- 结论：`controller/` 三个文件**被编译进产物却只服务测试**，生产行为仍由 `AimThread.cpp` 内联的那一份决定。

风险：改控制逻辑时改错文件不会被任何生产测试发现（因为测试测的是那份没人跑的抽象层）。
建议：二选一并明确写进文档——(a) 把生产链接到 `PidController`，AimThread 只留调度（推荐，但要先确认 `test_real_model`/`test_pid1` 能兜住行为等价）；(b) 删除 `controller/` 层，把测试改为直测 `AimThread`。**不要维持现状。**

**P1-2 层次反向依赖：`controller/` 依赖 `aim/`。**
证据：`core/src/controller/PidController.hpp` 第 10 行 `#include "aim/Pid1Controller.hpp"`。
这是 P1-1 的直接后果（下层为了封装上层的东西而反向 include）。修 P1-1 时顺带解决：把 `Pid1Controller.hpp` 下移到 `controller/`，或把 `PidController` 上移到 `aim/`。

**P1-3 巨石文件：单文件承担整个模块。**

| 文件 | 行数 | 体积 | 说明 |
|---|---:|---:|---|
| `plugins/web/templates/index.html` | 16,051 | 522 KB | 主面板整页 |
| `plugins/web/static/legacy/app.js` | 12,048 | 450 KB | 旧前端主逻辑 |
| `plugins/web/bin/ttbox-web.py` | 5,019 | 220 KB | 后端**单文件 206 个顶层 def/class** |
| `plugins/web/static/legacy/style.css` | 6,558 | 122 KB | 旧样式 |
| `core/src/app/Application.cpp` | 1,878 | 93 KB | 装配 + 生命周期 + 各子系统接线全在一处 |
| `usbproxy/proxy.cpp` | 1,652 | 55 KB | 代理主体 |
| `scripts/ttbox_m207_accept.py` | 1,196 | 54 KB | 验收脚本 |

判定：**不是所有大文件都该拆**。`index.html`/`app.js`/`style.css` 是 1:1 采用的上游面板资产，有「布局冻结基线」护栏（`docs/handover/2026-09-17/控制台布局冻结基线-2026-09-18.md`、`plugins/web/tests/test_web_console_parity.py`），动它要付出代价而收益低 —— **建议保留**。
真正值得拆的是两个：
- `plugins/web/bin/ttbox-web.py`（206 个顶层定义挤在一个文件，任何改动都要全局搜索）。
- `core/src/app/Application.cpp`（1,878 行，装配 + 生命周期 + 接线混在一起，且是 core 的启动必经点）。

建议：拆之前先用现有测试建立护栏（web 侧已有 9 个 pytest + `test_web_console_parity.py`；core 侧有 `test_application.cpp` 与 `test_lifecycle_stress.cpp`），按「路由 / 配置翻译 / 授权投影 / 生命周期」切分，一次只切一块。

**P1-4 `mouse/` 目录职责过载（28 文件混四类关注点）。**
现状分类：

- 选择与坐标：`TargetSelector`、`AimPointProfile`、`CoordinateTransform`、`FovAngle`
- 状态与跟踪：`AimStateMachine`、`AimTracker`、`OneEuroFilter`
- 输出整形（生产在用）：`PullCurve`、`ContinuousLead`、`PersonalTrajectoryShader`、`PersonalMotion`、`RecoilController`
- 输出整形（**只有测试在用**）：`MotionController`、`MotionMerge`、`Humanize`、`Deadzone`、`OutputScale`、`RateLimit`
- 类型与边界：`MouseTypes`、`IMouse`、`MouseRouter`

证据：后 6 个各自的反向引用数均为 **1**，且那 1 个都是 `core/tests/test_mouse.cpp`；`AimThread` 的 include 列表里没有它们（它用的是内联版，见 P1-1）。
建议：把后 6 个要么并入生产链（与 P1-1 一起做），要么删掉。**「有实现、有单测、但生产不用」是这套代码里最容易骗人的状态。**

**P1-5 `platform/` 随包出货但运行期不可达。**
证据：仓内文档已实测确认——`docs/handover/2026-09-17/代码梳理-批次014-交付总结-2026-09-17.md` §3 附注：「`platform/` 在运行期结构上不可达（无进程引用），可删，但必须随 release 一起出货——与 `fhs_init.sh:382`、`pyproject.toml` 的 testpaths/packages、`RELEASE_MANIFEST.template.json` 注释、板端既有目录共 **6 个删除耦合点**」。
建议：**不要单独删**。等发版窗口，按那 6 个耦合点逐条清理后一次性移除。本报告只是把它登记为「已知 + 有据」的债，不是新发现。

**P1-6 文档口径互相打脸：预测功能的状态两处不一致。**
证据：`docs/product/features/prediction.md` 说 `AimTracker` 已实现且「在 AimThread 中已接入（第 15 阶段）」（代码属实，`AimThread.hpp:121` 确有 `AimTracker tracker_;`）；而 `docs/product/TTBOX_FEATURE_MATRIX.md` 把 T031 Prediction 标为 🔵 PLANNED 且 Core 列为空。
建议：统一为一句话——「核心已接入，缺 Web 参数与开关」。否则续做时验收标准无从写起。

**P2-4 systemd unit 双份并存且已漂移（仓内自述）。** `plugins/web/config/README.md` 与 `plugins/preview/config/README.md` 都写着「双份并存且已漂移」，指出副本缺 `User=`/`Group=`/`PYTHONPATH`/`[Unit]` 段，且 `ExecStart` 指向旧布局。这是**已被文档记录但未修**的缺陷，建议并入下一次部署类改动。

## 五、不建议动的地方（避免过度重构）

1. **不要重排顶层目录。** `CONVENTIONS.md` §一 明确：本仓真正的架构维度是「出货物边界」（payload 白名单 / FHS release 树 / 编译期 `TTBOX_PROJECT_ROOT` / `scripts/` 路径锚），不是代码分层。重排目录会同时打破 `ttbox_fhs_init.sh` 的白名单、`pyproject.toml` 的 packages、门禁的路径锚 —— 收益低、风险高。
2. **不要动 `plugins/web/templates/index.html` / `static/legacy/*`。** 它们是 1:1 采用的上游资产，有布局冻结护栏与 `test_web_console_parity.py` 守着；改动会同时触发视觉回归与验收脚本失败。
3. **不要为了「统一风格」给每个 `.cpp` 配接口层。** 当前 `core/src/` 的头文件绝大多数是 header-only 实现（`.hpp` 8,396 行 vs `.cpp` 38,284 行），这是本仓的既有风格且工作良好。P1-1 的教训正是「多一层抽象却没接线」。
4. **不要在没有测试护栏时拆 `Application.cpp`。** 它是 core 的启动必经点，改错等于板子起不来。
