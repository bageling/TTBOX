> 独立缺陷记录（M2.07.1 收口批）。**新增章节，不改写历史**。相关历史：D-D（云态重启保持，B24）、
> F2（拒绝真因可见）、F10（default.json 0640）。

- **缺陷号**：F11
- **来源**：M2.07.1 收口批，QA（software-qa-engineer）独立对抗性验证挖出；team-lead 读码确认并**扩大范围**
- **严重级别**：**P0** —— 免密面板下**局域网内任意人可远程关停 AI**
- **影响版本**：core 1.4.1 / 1.4.2
- **修复版本**：core **1.4.3**（源码 commit `70d07f7`）
- **回归锚**：板端 **B25**（`scripts/ttbox_m207_accept.py`）+ 宿主 `test_license_daemon`（+4 用例）

---

## 1. 根因

`core/src/auth/LicenseDaemon.cpp::activate()` 有**三条拒绝路径**，它们在验签/结构校验失败时
会改写**内存授权态**，却**不回滚**：

| # | 拒绝路径 | 修前行为 |
|---|---|---|
| ① | `parse_license_card` 失败（L129-139） | 写 `status_.state = kInvalidCard` + `last_error`，**不动** `cloud_license_` |
| ② | 防降级 `LICENSE_DOWNGRADE_REJECTED`（L145-160） | 只写 `status_.state = kInvalidCard` |
| ③ | 验签失败（L173-193） | 清 `card_plain_` + 写 `last_error`；**`cloud_license_` 已被步骤②无条件置 false，且不回滚** |

关键点（team-lead 读码指出的、比 QA 初报更大的范围）：
- 步骤②（装卡）**在验签之前**无条件 `cloud_license_ = false;`。这一行**不能简单后移** ——
  因为 `verify_now_blocking()` 有 D-D 加的云态短路 `if (cloud_license_) {…}`，不清云态就**永远不会**
  真去验离线卡。
- 因此**云激活态**下，一次被拒的 `ACTIVATE` 会把云态打掉，直到**重启 core** 才由
  `restore_cloud_doc_locked()` 恢复；且①②虽没动 `cloud_license_`，却把 `status_.state` 踩成
  `kInvalidCard`，而 `verify_now_blocking()` 的云态短路**只复位 `status_.bind_device`、不复位 state**
  ⇒ `/api/license` 显示未激活、`pipeline_allowed()` 变 false（AI 关）。

**为什么是 P0**：面板**免密**（M2.07 需求①：无 token 直达 `/api/config|state|license`）。
`POST /api/license/activate` 亦在免密白名单内 ⇒ **局域网内任何人**发一个「结构非法」或
「坏签名」的 POST，即可关停 AI（拒绝服务 / 干扰对抗）。

QA 受控证据：
```
before: {activated=True, state=active, source=cloud}
POST /api/license/activate  {license_key: <card-badsig>}   （被拒）
after : {activated=False, state=unactivated, msg='offline card: signature mismatch'}
```

---

## 2. 影响面

- **触发条件**：core 处于**云激活态**（`source=cloud`）时，收到任一被拒的 `ACTIVATE`
  （非法 JSON body / 坏签名离线卡 / 降级卡）。
- **后果**：`cloud_license_` 丢失、`status_.state` 被踩 ⇒ **AI 被关**（`pipeline_allowed()==false`），
  且**不会自愈**直到 core 重启（web 心跳只在**到期/禁用**时才发 `deactivate`，此类拒绝不触发恢复）。
- **攻击面**：免密面板 ⇒ 局域网任意主机一条 `curl` 即可复现。
- **不触发**：离线卡激活态（非云）下，被拒卡**照旧**写 `kInvalidCard` + 原因（**F2 排障意图**，
  见 §3 反向护栏，未被本修复改动）。

---

## 3. 修法（行为级契约）

在 `activate()` **入口**快照完整授权态，三条拒绝路径**统一**回滚（唯一机制 `rollback_cloud_guard()`）：

```cpp
// 入口快照（cloud_license_ / status_ / card_plain_）
bool prev_cloud = false; LicenseStatus prev_status; std::string prev_card;
{ std::lock_guard<std::mutex> lk(mu_);
  prev_cloud = cloud_license_; prev_status = status_; prev_card = card_plain_; }
auto rollback_cloud_guard = [&]() {
    if (!prev_cloud) return;                 // 仅"调用前为云激活"才回滚
    std::lock_guard<std::mutex> lk(mu_);
    cloud_license_ = true; status_ = prev_status; card_plain_ = prev_card;
};
```

三条路径（parse 失败 / 降级 / 验签失败）在写完各自的诊断后，**统一**调用 `rollback_cloud_guard()`：

- **云激活态（`prev_cloud==true`）**：`cloud_license_ / status_ / card_plain_` **逐字段回滚** ⇒
  调用后 `/api/license` 与管线放行结果与调用前一致
  （`activated=true / state=active / source=cloud / features.capture=true`）。
- **非云激活态（`prev_cloud==false`）**：**保持既有行为** —— 把拒绝原因写进状态
  （`kInvalidCard` + `last_error`），供现场排障（F2 意图）。
- **合法离线卡（kValid）**：仍照常**"接管"**（`cloud_license_=false` + `save_doc` 落盘 + 返回 true）——
  回滚**只在被拒**时发生，成功路径完全不变。

> 设计取舍：采用「先写诊断 → 再统一回滚」而非「分支条件写」，使**三条路径共用同一回滚机制**，
> 变异检验能一次性覆盖全部三条（见 §4）。

## 4. 回归锚

### 4.1 宿主单测（`core/tests/test_license_daemon.cpp`，+4 用例，共 17 全绿）
| 用例 | 断言 |
|---|---|
| `activate_reject_preserves_cloud_state` | 云态下 parse 级 + 验签级拒绝 ⇒ 状态逐字段不变；`allow_run()` 仍真；`license.json` 不落盘；其后 `verify_now_blocking()` 走云短路仍真 |
| `activate_downgrade_reject_preserves_cloud_state` | 云态下防降级拒绝 ⇒ 状态逐字段不变 |
| `activate_reject_when_not_cloud_keeps_diagnostic_state`（**反向护栏**） | 非云态下拒绝仍写 `kBoundElsewhere`/`kInvalidCard` + `last_error` |
| `activate_valid_offline_card_takes_over_cloud`（**反向护栏**） | 合法离线卡仍接管：`doc_json=离线信封`、`doc_is_cloud=false` |

⇒ `activate_reject_preserves_cloud_state`（8 断言）与 `activate_downgrade_reject_preserves_cloud_state`
（3 断言）**双双变红**（15 passed / 2 failed）；还原后 **17/17 全绿**，`ctest` 全量 **28/28 绿**。
