## 3. 本批修复的三个缺陷

### D-A（P0）｜`/opt/ttbox/config` 组不可写 ⇒ **终端用户永远无法激活**
- **根因**：该目录为 `root:root 0755`，而 web 服务 `User=ttbox`。`CloudSessionStore.save()`
  的原子写（tmp + rename）需要的是**目录**写权限 ⇒ EACCES ⇒ `ttbox-web.py:4389` 返回 500
  「云端验证成功，但会话落盘失败」⇒ **core 的 `ACTIVATE_CLOUD` 根本未被调用**。
- **性质**：F9 同类缺陷在新状态路径上复发（F9 修的是 `/etc/ttbox`，本批新引入的
  `cloud_session.json` 落在从未开权的目录）。
- **修复**：`scripts/ttbox_fhs_init.sh:120` 改为 `root:ttbox 0775`，并补**显式幂等
  `chgrp`+`chmod`** —— `install -d` 对已存在目录不改属组/权限，光改参数救不了存量设备。
  `RELEASE.md §7` 增排障条目（对齐 F9 体例）。
- **实证**：开权后激活立即 200、`cloud_session.json` 落盘（`-rw------- ttbox ttbox`）、
  `/api/license` 翻绿、≤60s 心跳 `online=true`。

### D-B｜验收脚本缺 web 就绪等待 ⇒ **5 项被误判为 FAIL**
- **根因**：`ttbox_m207_accept.py:280 restart_web()` 无就绪等待；`_restore_activated()`
  只等 core 不等 web。B16 在 `finally` 调用它 ⇒ 其后所有用例都打在**正在启动**的 web 上
  （web 冷启要 import numpy/cv2）。
- **修复**：新增 `wait_web_ready()`（`WEB_READY_S=90`），`restart_web()` 与
  `_restore_activated()` 收尾调用；`status==0` 一律 SKIP 而非 FAIL。
- **注**：离线卡 B23/B8/B10/B11/B6·ota 的"FAIL"**全是误判**；手工复测逻辑本身正确。

### D-D（P0）｜云激活过 core 重启会丢 ⇒ **每次重启掉回激活页**
- **现象**：重启前 `activated=True`；重启后**立刻且永久** `activated=False`。
- **根因（三处，缺一即丢）**：
  1. `Application::resolve_license_card()` 把 store 里的 **cloud 形文档当"离线卡"**交出；
  2. `LicenseDaemon::verify_now_blocking()` 无 `cloud_license_` 守卫，拿该文档走离线验签
     （必败）⇒ `apply_check_result()` 覆盖 `restore_cloud_doc_locked()` 刚建立的 kValid；
  3. `thread_loop()` 的 **`card_plain_` 非空分支**无守卫，周期性继续离线验签。
- **关键证据**：`LicenseDaemon.cpp 云端授权恢复: state=2`（恢复成功）→ **61 秒后**
  `Application.cpp:836 授权未通过`。
- **修复**：① `verify_now_blocking()` 云态持锁短路（不调 verify/不调 apply_check_result）；
  ② `StoreLoadResult::doc_is_cloud` 落成**单一真源**（`LicenseStore.cpp:247` 解析），
  `resolve_license_card()` 只消费、不手搓字符串；③ `thread_loop` 非空分支加守卫。
  另加 2 条 core 单测（含反向护栏）+ 新增验收用例 **B24**。
- **实证（修复后）**：90s / 18 采样点全程 `activated=True`；日志变为
  `Application.cpp:842 授权通过 state=2`，`授权未通过` 不再出现。

### 附带修复
- `core/src/auth/TtboxCanonical.hpp` 尾换行 latent 冲突已订正（与云端
  `clientSigningString` 逐字节一致，末尾**无**换行）+ 测试断言同步。
