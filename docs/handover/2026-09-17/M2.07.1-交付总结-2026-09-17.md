## 3. 本批修复的缺陷

### F11（P0）｜被拒的激活请求会清掉云激活 ⇒ 免密面板下任意局域网请求可关 AI
- **现象**：云激活态下 `POST /api/license/activate` 投一张**被拒**的卡 ⇒ `activated` 从 `True` 变 `False`、`state` 变 `unactivated`，直到重启 core 才由 `restore_cloud_doc_locked()` 恢复。
- **根因**：`core/src/auth/LicenseDaemon.cpp::activate()` 在**验签之前**无条件 `cloud_license_ = false`（这步本身必要 —— 不清就绕不开 D-D 加的云态短路、永远不会真去验离线卡），但**三条拒绝路径**（parse 失败 / 防降级 / 验签失败）都**没有回滚**授权态。前两条更隐蔽：虽不动 `cloud_license_`，却把 `status_.state` 踩成 `kInvalidCard`，而云态短路不会把 state 复位。
- **影响面**：面板按 M2.07 需求①是**免密**的 ⇒ 局域网内任何人一个 `{}` 空 body POST 即可关掉 AI。恢复需重启 core 或重新激活。
- **修法**：`activate()` 入口快照 `{cloud_license_, status_, card_plain_}`；三条拒绝路径**先写各自诊断（保 F2 排障意图）、再统一调用 `rollback_cloud_guard()`**（仅"调用前是云激活"才回滚）；合法离线卡仍照常接管（`cloud_license_=false` + 落盘）。**未改动 `cloud_license_=false` 的原有次序**。
- **回归锚**：新增板端用例 **B25**（云激活态下投 ① 非法 body ② `card-badsig` ③ 空 body ⇒ 授权字段逐字段不变、心跳仍 online）+ 4 条宿主单测。
- **实证**：B25 PASS（三次被拒 HTTP 400，`before/illegal/badsig/empty` 四组字段全同）；QA 自写探针 5/5 PASS（另加打 `card-expired`/空 key）；变异检验（`rollback_cloud_guard` 置 no-op）⇒ 两个云态契约用例**变红**（15 passed / 2 failed），还原 + `touch` 后 17/17 绿、`ctest 28/28`。

### T1（安全）｜生产密钥硬编码在源码 + example 文件写真实值
- **发现**：`plugins/web/lib/cloud_client.py:37` `DEFAULT_APP_SECRET` 是**生产真值**；`config/cloud.example.json` 里也是真值（含真实隧道 URL）；仓库根记账文件亦抄有真值（主理人自行脱敏）。
- **修法**：`DEFAULT_APP_SECRET` / `DEFAULT_LICENSE_BASE_URL` 改空串（保留符号以兼容既有 import）；example 改占位符；`.gitignore` 拦截真实凭据落点。
- **语义变化（必须写准，不是"零语义变化"）**：`cloud_client.py:121` 是 `... .get('app_secret') or DEFAULT_APP_SECRET`。配置缺 secret 时，**旧代码会回落到硬编码真值并签名成功**，新代码回落空串 ⇒ 走 `not_configured` **fail-closed**。这是**期望的加固**。
- **实证**：缺 secret 的 **6 种形态**（无键/空串/None/全空白/无 cloud 段/cloud 非 dict）全部 `not_configured`，且**到达 mock 云端的请求数 = 0**（证明无任何内置值参与签名）；有 secret 时签名 == 用配置值复算的 HMAC 且热读生效。

### T2（隐患）｜`default.json` 出厂世界可读 + 写侧丢属组
- **根因**：`scripts/ttbox_m207_accept.py::atomic_write_json()` 保了 `mode` 却没保**属主** ⇒ root 侧 tmp 文件以 `root:root` 建成再 `os.replace` ⇒ 一旦收紧成 `0640`，`User=ttbox` 的 web 就 EACCES ⇒ 云端凭据丢失（激活 502「云端凭据未配置」）。这正是 M2.07 曾把"权限收紧"回退掉的原因。
- **修法**：① `atomic_write_json` 在 posix + euid==0 时 `os.chown(tmp, st.st_uid, st.st_gid)`；② `ttbox_fhs_init.sh` 加**显式幂等** `chgrp ttbox` + `chmod 0640`（`install` 对已存在文件不生效，救不了存量设备）；③ 订正 `config/README.md` 与实际不符的 0600/0700 口径。
- **实证**：板端 `-rw-r----- 1 root ttbox`；**root 重写两次后属组仍是 ttbox**；激活 200、无 502；QA 另做**负对照**（用无 chown 的旧脚本写 ⇒ 属组果然变 `root`）反证修复有效。

### T3（覆盖缺口）｜`resolve_license_card()` 守卫无宿主单测
- 该函数未链接进 `test_license_daemon`，变异不变红，只靠板端 E2E 兜。
- **修法**：把判定抽成 `LicenseStore.hpp:44` 的**唯一真源** `inline std::string offline_card_doc(const StoreLoadResult&)`；`Application.cpp` 改为调用它（**不留两份逻辑**）；补 4 条单测（含"cloud 文档不得当离线卡"反向护栏 + "离线信封正常交出"正向）。
- **实证**：变异（注释守卫）⇒ `test_license_daemon` 变红（`:87`/`:430` 两条 FAIL）；还原 + `touch` ⇒ 13/13 绿、`ctest 28/28`。

## 4. 主理人独立复核的重要发现（否掉了一条结论）

**T4 的"可复现锚"原本不成立**：出货 core `d1b0276f…` 构建于 `21:56:48`，而 `Application.cpp` 改于 `22:35:26`、`LicenseStore.hpp` 改于 `22:37:35` —— **源码晚于二进制**，提交信息里那句 "core d1b0276f" 不可复现。

**订正与自证**：重建 1.4.2 时用**两次独立 clean build**（一次建到临时目录、一次建到规范目录）得到**逐字节相同**的 `sha256/md5/buildid`。临时目录那次 `vector_hash` 不同**不是不可复现** —— `vector_hash` 只覆盖配置向量（toolchain/sysroot/configure_args/rknnlib sha，**不含 commit**），而 `configure_args` 内嵌 `-B <构建目录>` 路径 ⇒ 换目录名必然变 hash，与产物字节无关。规范目录重建的 `vector_hash` 与留档吻合。
