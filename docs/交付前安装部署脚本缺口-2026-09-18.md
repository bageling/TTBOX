# 交付前安装部署脚本库缺口审计（2026-09-18）

> 一次性报告（非活真源）。审计对象：`scripts/` 的安装部署链、`deploy/` 的服务与配置。
> 只回答一个问题：**装、发、卸、修这条链上，缺什么。** 不改代码（代码冻结期内）。
> 定案登记见 `docs/交付前逐项定案台账-2026-09-18.md` §「安装部署脚本缺口（D 组）」。

## 一、审计口径

三路独立探查，角度不重叠：生命周期完整性（逐个环节反查有无对应脚本）、脚本健壮性（8 项逐条核对）、出货口径与孤儿脚本（三处排除清单对比 + unit 引用核查 + 调用方反查）。

三路汇报里的 P0 / P1 断言，**由主理人逐条读源码独立复验**，不采信汇报结论。下面每条都标了复验结果。
本报告已否掉 2 条汇报里的误报，见 §七。

搜索口径：排除 `.git/`（`.git/_recovery/` 里有旧副本，会造成幽灵命中）与 `game-assist-lab/`（与本项目无关的独立工程）。

## 二、结论摘要

| 级别 | 条数 | 一句话 |
|---|---|---|
| P0 会毁数据 / 假成功 | 3 | 构建脚本能 `rm -rf` 任意目录；安装失败仍 exit 0；OTA 调度器无条件报成功 |
| P1 出货链 / 门面断点 | 6 | 出货 web 引用的 4 个脚本与目录不在 payload；门禁只查软链不查文件；面板整套更新 UI 跟后端三处对不上 |
| 硬缺口（完全没有脚本） | 5 | 卸载、备份恢复、依赖安装、统一顶层入口、出厂重置（后者已有"不做"决策） |
| 有脚本但不完整 | 4 | 升级缺版本发现、回退只能回一版且不阻断、修复不管断链、迁移只迁模型 |
| 不是缺口（已定论） | 7 | 刻意豁免 5 处 + 否掉误报 2 条 |

用一句话概括现状：**这台盒子的"装、发、回、修"四件事有脚本而且写得不错；"卸、备份、装依赖、统一入口"基本是空白。** 另外"装了之后 web 会去调两个不会存在的脚本"这一类组合缺口，之前没人查过。

## 三、P0：会毁数据或会假成功（三条，均已独立复验）

### D01 构建脚本可以 `rm -rf` 任意目录

`scripts/ttbox_build_release.sh:74-78` 把环境变量 `TTBOX_BUILD_DIR` 直接当路径用：

```
BUILD_DIR="${TTBOX_BUILD_DIR:-build-aarch64-t114}"
case "$BUILD_DIR" in
  /*) ;;                                        ← 绝对路径原样放过
  *) BUILD_DIR="${REPO}/${BUILD_DIR}" ;;
esac
```

紧接着 `:125`：

```
echo "[release] §3 clean：rm -rf ${BUILD_DIR}"
rm -rf "$BUILD_DIR"
```

中间没有任何白名单守卫，也没有 dry-run。把它设成 `/opt/ttbox`、仓库根、或用户主目录，脚本会照删不误。这是本次审计里唯一"输入可控且直接执行破坏"的动作。

**一处更正**：汇报把它写成"会删客户数据"，这夸大了。这脚本跑在**构建机**上（Windows/WSL），不是板端，所以后果是构建机上任意目录被删，不涉及板端客户数据。但仓库根被删同样是灾难，严重度不降级。

### D02 安装失败仍然报成功

`scripts/ttbox_fhs_init.sh:487`：

```
sync_tree "$VER" || echo "  [!] sync_tree 未完成（见上），跳过后续激活相关步骤"
```

`sync_tree` 在找不到合格的 core 二进制（即 `detect_build_dir` 失败）时会 `return 1`（`ttbox_fhs_init.sh:341-345`，函数内还有 `:429/:432` 的 `|| rc=$?` 与 `:435 return $rc`）。这个返回值被 `|| echo` 吃掉之后，脚本继续往下跑完，最后打印 `== 完成。后续步骤 ==`，**退出码 0**。

准确说它不是完全静默——那行 `[!]` 警告会打出来。但退出码 0 这件事足够让任何外层脚本、CI 或自动化判成安装成功。板端表现是 `current` 没建立、或仍然指向旧版本，服务起不来。

顺带一处语义不一致：同一个函数里，`:366` 和 `:372` 用的是 `exit 1`（终止整个脚本），`:344` 用的是 `return 1`（只返回给调用方）。两种失败语义混用，正是上面这个吞没能成立的前提。

### D03 OTA 调度接口无条件报成功

`plugins/web/bin/ttbox-web.py:1947-1957`（`_ota_install_impl`）：

```
unit = 'ttbox-update-%d' % int(time.time())
updater = '/opt/ttbox/current/scripts/ttbox_ota_updater.py'
subprocess.Popen(['systemd-run', '--unit', unit, '--collect', '--on-active=2s',
                  updater, url, key_id])
return jsonify({'ok': True, 'scheduled': unit})
```

`Popen` 只要 fork 成功就返回，**不检查 updater 脚本是否存在、不检查 systemd-run 是否可用、不等结果**。而 `updater` 指向的 `/opt/ttbox/current/scripts/ttbox_ota_updater.py` 根本没被打进 payload（见 D05）。**直调 API 时**会稳定返回 `ok:true, scheduled:...`，实际 systemd 瞬时单元立刻失败，什么都不发生 —— 这是 D05 的表现层放大。

但要更正一处初版写错的地方：**从面板点不到这里**。面板的 `installUpdatePlan()`（`index.html:11388-11408`）发的是 `{'plan': {...}}`，而 `_ota_install_impl` 读的是 `body.get('url')` / `body.get('key_id')`（`ttbox-web.py:1941-1943`），`url` 为空 ⇒ 先撞 `400 url is required`。所以准确说法是：**面板上是"报错"，接口上是"假成功"，两边都不对，修法也不同**（详见 D17）。

## 四、P1：出货链断点（5 条）

共同形状：**出货的代码硬编码了一个绝对路径，而那个路径下的文件不会被安装流程拷进去。** 门禁查的是"软链在不在"，不查"软链指向的那个文件在不在"，所以能一路绿着把功能废掉。

### D04 `lan_blocklist.sh` 未随包，且请求门禁静默放行

- 出货 web 硬编码：`plugins/web/bin/ttbox-web.py:1847` `LAN_BLOCKLIST_SCRIPT = '/opt/ttbox/scripts/lan_blocklist.sh'`
- payload 的 `scripts/` 只装两样：`scripts/ttbox_fhs_init.sh:404-407` 只 `tcopy` 了 `scripts/edid/`，再 `install` 了 `ttbox_ensure_services.sh`。**没有 `lan_blocklist.sh`。**
- `deploy/RELEASE_MANIFEST.template.json` 的 `scripts/` 项下也只有 `edid/edid_apply.sh`（`:14`）。

复验时发现比汇报更麻烦的一点，分两层：

1. **接口层会明说不可用**。`_run_lan_blocklist` 的未安装分支（`:1852-1857`）返回 `supported:false / "局域网黑名单脚本未安装"`，面板会显示这条消息。这层不算静默。
2. **但请求门禁不看这一层**。`_is_blocked()`（`:1432-1441`）只读返回里的 `blocked_ips`，空集合就相当于所有 IP 都不封禁，而它真正的用途是在 `:1521` 当门禁用：

```
if _is_blocked(request.remote_addr):
```

也就是说：面板上显示"脚本未安装"，但**门禁本身不会因此拒绝任何请求**，是 fail-open。客户看到一条提示也不会想到"现在任何人都不受黑名单约束"。

面板 UI 确实在现役页面里（`index.html:6081-6093` 的 `lanBlockSummary` / `lanBlockIpInput` / `scanLanDevicesButton`，JS 在 `:10710-10832`）——S1 减掉了无线页签，但这块黑名单面板保留了，所以它不是一个已经下线的功能。

### D05 `ttbox_ota_updater.py` 未随包，整条 OTA 链是断的

- 出货 web 硬编码：`ttbox-web.py:1950` `/opt/ttbox/current/scripts/ttbox_ota_updater.py`
- payload 的 `scripts/` 只装 edid 与 ensure（同 D04）⇒ **updater 自身未出货**
- 而 updater 内部还有两个依赖，也都不出货：
  - `scripts/ttbox_ota_updater.py:46` `KEYS_DIR = Path(__file__).resolve().parents[1] / "tools" / "ota" / "keys"`
  - `scripts/ttbox_ota_updater.py:48` `INSTALL_SCRIPT = "/opt/ttbox/current/scripts/ttbox_release_install.sh"`

`tools/` 整目录不在 payload：`grep -in "tools" scripts/ttbox_fhs_init.sh` **零命中**（复验过两次）。`tools/ota/keys/` 在仓库里存在（`tools/ota/keys/ttbox-ota-2026a.pub`，113 字节）。

所以这条链的现状是：**要修，得一次补齐三处**（updater 脚本 + `ttbox_release_install.sh` + `tools/ota/keys/`），只补一处仍然不通。

### D06 门禁只断言软链存在，不断言软链里的文件存在

`scripts/ttbox_release_verify.sh:36-37` 的过渡软链断言清单：

```
"plugins:current/plugins"   # 插件发现 + 旧 web unit 路径
"scripts:current/scripts"   # lan_blocklist / edid 工具链 import（wifi_manager 已移出）
```

注释里明写着这条软链是"给 lan_blocklist 用的"，但门禁只验证软链**可解析**，不验证 `current/scripts/lan_blocklist.sh` **存在**。同理 `release_install.sh:116` 附近的过渡软链注释也声称覆盖 LAN-blocklist。**这是 D04/D05 能长期不被发现的原因**，也是一个独立的校验缺口：门禁的断言粒度比它的注释窄。

### D07 payload 排除清单三处形状不一致

三处口径分别是：`ttbox_fhs_init.sh`（`:222` 的 `tcopy --exclude` + `:383-385` 的整树 `tcopy` 后按文件 `rm`）、`ttbox_release_install.sh:81`（`tar --exclude` 按模式）、`ttbox_release_verify.sh`（**没有任何"应存在 / 应不存在"的文件清单**）。

| 项 | fhs_init | release_install | release_verify |
|---|---|---|---|
| `__pycache__` / `*.pyc` / `.git` | ✓ `:222` | ✓ `:81` | 无断言 |
| `tests` | ✓ E02 | ✓ E02 | 无断言 |
| `plugins/web/api_v1.py` | ✓ `rm :383` | ✗ | ✗ |
| `plugins/web/framework_api.py` | ✓ `rm :384` | ✗ | ✗ |
| `plugins/web/static/legacy` | ✓ `rm -rf :385` | ✗ | ✗ |
| `platform/` | ✓ 隐性（不 tcopy） | ✗ | ✗ |
| `scripts/wifi_manager.py` | ✓ 隐性（不 install） | ✗ | ✗ |

两个问题：一是**形状不一致**——一处是"整树拷完再删文件"，一处是"按模式排除"，靠语义对齐而不是同一份清单，新增一项极易只改一处（当前 api_v1 / legacy 就是这个状态）。二是 **verify 完全没有"不得存在"断言**，E02 的 `tests` 只在 verify 侧缺断言，所以自己排了没排干净没人知道。

需要说清楚的是：这 5 项"只在一处"**不构成漏出货**，因为 `release_install.sh:225` 是 `tar -C "$payload"`，打的是传进来的 payload（payload 由 fhs_init 的白名单造出，这 5 个文件本来就不在里面），不是仓库根。所以这是**校验缺口与维护风险**，不是当下的漏货缺陷。这条与汇报里的说法有出入，见 §七。

### D17 面板的更新界面是门面：UI 全套在，后端全套空，还有三处接口对不上

面板（自包含单文件 SPA）里有一整套更新界面，全在现役代码里（`plugins/web/templates/index.html:6003-6039`）：

| 控件 | 位置 | 点下去会怎样 |
|---|---|---|
| `checkUpdateButton`「检查更新」 | `:6007`，接线 `:11373-11386` → POST `/api/update/check` | 后端 `return not_supported`（`ttbox-web.py:1992`）⇒ 400，界面报错 |
| `switchUpdateVersionButton`「切换版本」 | `:6008`，接线 `:11148-11162` → **POST** `/api/update/versions` | 后端只注册了 `@app.get`（`ttbox-web.py:1984`）⇒ **405 方法不允许** |
| `cleanupUpdateStatusButton`「清理卡住状态」 | `:6009`，接线 `:11410` 起 → POST `/api/update/cleanup-stuck` | 后端 `return not_supported`（`ttbox-web.py:1997`）⇒ 400 |
| `installUpdateButton`「安装更新」 | `:6010`（默认 disabled），接线 `:11388-11408` → POST `/api/update/install` | payload 形状对不上后端，见下面第 2 条 |
| `updateStatusPill` / `updateSummary` / `updateProgressPanel` / `updateProgressBar` / `updateReleaseNotes` / `updateVersionDialog` | `:6003-6039` | 数据源 `/api/update/status` 只是 systemd 单元状态投影，其余永远空 |

三处接口对不上，每一处都足以让功能不通：

1. **method 对不上**：面板发 `POST /api/update/versions`，后端只注册了 `GET` ⇒ 405。
2. **payload 形状对不上**：面板发 `{'plan': {...}}`（`index.html:11398`），后端读 `body.get('url')` / `body.get('key_id')`（`ttbox-web.py:1941-1943`）⇒ 400 `url is required`。
3. **能力对不上**：product 文档把 7 个更新端点全标 `⛔ REMOVED`（`docs/product/TTBOX_WEB_FEATURE_MATRIX.md:180-186`），并写明「离线更新能力（`scripts/update_engine.py` 及其 socket）已按产品决策删除，下列命令不再规划实现」（`docs/product/TTBOX_API_CONTRACT.md:210-211`）；`scripts/` 下也确实没有 `update_engine.py` 了。

也就是说：**这套更新能力从来没实现过**——文档原话是"原为新增计划"。留下来的只有 UI 和几个派生自旧计划的端点占位，而每一次点击都是报错。

附带一处文档自打架：`TTBOX_API_CONTRACT.md` 小节标题写「下列命令不再规划实现」，表格里 `CANCEL_UPDATE` / `ROLLBACK` / `GET_LOG` 三条却还标着 🔵 PLANNED。

处置只有两条路：要么把后端做出来（面板那三处不匹配必须一起改，否则接上了照样点不动），要么把 UI 一起摘掉。留着一套必然报错的按钮，和 D03 是同一类问题。

## 五、硬缺口：完全没有脚本（5 条）

### D08 卸载

全仓没有系统级卸载脚本，也没有卸载步骤的文档。要卸掉得人工清一串：`/opt/ttbox`、`/etc/ttbox`、`/var/lib/ttbox`、`/var/log/ttbox`、`/run/ttbox`、ttbox 用户与组、7 个 unit（含 `ttbox-ensure.timer` 这种容易漏的）——**没有任何一处记录了这份清单**。

复验：顶层入口 `install.sh / uninstall.sh / upgrade.sh / setup.sh / bootstrap.sh / manage.sh / deploy.sh` 七个全部不存在；`scripts/` 下按名字匹配只有 `a9_pkg_install.sh` / `a9_pkg_rollback_demo.sh`（见 §七，是 HID 包演示，与设备安装无关）。

需要决策的点：要么写卸载脚本，要么在文档里明确定义"不提供卸载，换盘即弃"。**留着空白是最差的选项**，客户问起来没有答案。

### D09 备份与恢复

唯一称得上备份的是 EDID 改 boot 镜像前的备份（`scripts/edid/edid_patch_boot_image.sh:4,10` → `/var/lib/ttbox/boot_image_backups/`）。要保命的三处——`/etc/ttbox`（客户配置与凭据）、`/var/lib/ttbox`（模型 / HID 包 / 授权）、`/opt/ttbox/releases`——没有打包、没有校验、**恢复连文档都没有**。

文档里只有零星的人肉习惯：`docs/ops/修改指南.md:130`、`docs/ops/问题排查.md:149`（改前 `cp 文件 .bak-$(date)`）、`docs/handover/2026-09-17/RELEASE.md:222`（手动备份 license.key）。都是"人记得就做"，不是流程。

后果很直接：**换板 = 客户数据和授权全丢。**

### D10 依赖安装与前置自检

`deploy/DEPENDENCIES.md:8-17` 把 apt 包（cmake / g++ / librga-dev / libjpeg-dev / libopencv-dev / python3-flask / python3-waitress / python3-numpy）列成一张"手工 apt-get install"表；`:30-42` 手工放 rknn 头文件与模型；`:48-58` 手工改 `/boot/extlinux/extlinux.conf` 加 overlay，再手工跑 `deploy/inject_edid.sh`。

没有任何脚本做安装或校验。全仓 `apt-get install` 只在两处出现，而且都是**报错提示文案**（`scripts/ttbox_ota_updater.py:40`、`tools/ota/ttbox_ota_sign.py:36` 提示装 cryptography）。也就没人检查 overlay 是否生效、`/dev/video0` 是否存在。

### D11 统一顶层入口

没有 `install.sh` 这类入口，也没有 Makefile / justfile / Taskfile。现行的"一条链"是隐式串起来的：

```
ttbox_build_release.sh   → 编译 + 门禁
ttbox_fhs_init.sh <ver>  → 首装 / 浇筑
ttbox_release_install.sh <ver> <payload> --activate  → 发布换链
ttbox_ensure_services.sh → 自愈
```

这条串链只写在脚本自己的尾巴和手册里（`scripts/ttbox_fhs_init.sh:498-503`、`deploy/DEPENDENCIES.md:123-131`、`docs/handover/2026-09-17/RELEASE.md:111-126`）。而且**首装入口在一线文档里全部缺席**：`README.md` 全文没有 `fhs_init`、`docs/README.md:95-103` 的运维路线没有安装条目、`docs/ops/` 六个文档没有一个描述首次安装。首装命令只散落在 `docs/handover/` 里。

顺带：`README.md:112-124` 的"板端安装路径"还是旧直铺布局（bin/config/web/models/src），没有 `releases/<ver>` + `current`，与 `deploy/DEPENDENCIES.md:88-108` 的口径冲突。

### D12 出厂重置（已有"不做"决策，需书面确认）

既无脚本也无文档。设备级重置在全仓零命中；仅有的 3 处命中全是界面样式重置（`plugins/web/static/designer.js:349,362`、`plugins/web/templates/designer.html:19`）。

但这一条**有决策背景**：工作区记忆记录过用户拍板"只做镜像包和程序"⇒ 恢复出厂不做。所以它应该归成"有意缺失，需在交付文档里写明确"而不是"遗漏"。写清楚比补齐更省事——客户手册里得能查到这句话。

## 六、有脚本但不完整（4 条）

### D13 升级：链路通，但"发现新版本"是空的

发布换链做得扎实：`ttbox_release_install.sh:397-437`（发布 → 原子换链 → unit 断言 → 过渡软链 → daemon-reload + restart → 30 秒健康检查 → 失败自动回切）；OTA 侧 `scripts/ttbox_ota_updater.py` 有 sha256 + Ed25519 双因子与失败回滚。

缺的是"有没有新版本"这件事：

- `/api/update/versions`、`/api/update/check`、`/api/update/cleanup-stuck` 三个接口直接 `return not_supported`（`ttbox-web.py:1986-1997`）⇒ 升级的 url 与 key_id 必须人工提供，面板上的"切换版本"点不出任何东西。
- `plugins/upgrade/` 是空壳：`plugins/upgrade/plugin_entry.py` 全文只有 `import signal` + `signal.pause()`，`config/upgrade.json` 是 `{}`，`bin/ttbox-upgrade` 只是 `exec python3 ../plugin_entry.py`。名字像升级能力，实际不做任何事。
- 升级前没有任何数据备份或兼容性检查步骤（与 D09 同源）。

### D14 回退：能回，但只回一版且不阻断

`ttbox_release_install.sh --rollback` → `do_rollback()`（`:459-484`）：current 指回上一版 → reload_and_restart → 健康检查。三个不足：

1. 只能回**上一版**——取 list_versions 里第一个非当前版本（`:468-473`），没有 `--rollback <ver>` 指定版本。
2. 回退后健康检查失败只 warn 不阻断：`:480-483` 打印"回滚后健康检查未通过（请人工介入）"，**退出码仍是 0**。这与 D02 是同一类问题（失败不体现在退出码上）。
3. 文档与脚本不同步：`docs/handover/2026-09-17/RELEASE.md:232-238` 还在教人工 `ln -sfn /opt/ttbox/releases/<prev> /opt/ttbox/current && systemctl restart ...`，没引用现成的 `--rollback`。

### D15 修复：unit 级自愈扎实，发布系统本身坏了没人管

有的部分做得不错：`ttbox_ensure_services.sh` 幂等同步 unit（契约见文件头 `:1-31`，受管清单 `:40`，原子替换 `:120-155`，候选写完整性护栏 `:125`）；`deploy/systemd/ttbox-ensure.timer` 开机 2 分钟 + 每 10 分钟；`ttbox-core.service:8-9,33-34` 是 `Restart=always` + `StartLimitBurst=5/300s`。重装式修复也可用（fhs_init 全流程幂等）。

缺口在于覆盖范围：**current 断链时 ensure 明确"全部跳过、exit 0"**（`ttbox_ensure_services.sh:13-15`）⇒ 发布系统本身坏了没有任何自愈或告警，timer 每 10 分钟"成功"地什么都不做。配置损坏、二进制损坏、磁盘满、`systemctl reset-failed` 这些也都不管，只有手工文档（`docs/ops/问题排查.md:87-100`、`RELEASE.md:224`）。没有"一键诊断"脚本——`ttbox_release_verify.sh` 是只读体检，不做修复。

### D16 迁移：只迁了模型目录

唯一的迁移逻辑是 `ttbox_fhs_init.sh:441-452` 的 `seed_models_from_legacy()`，把旧 `/opt/ttbox/models` 搬到 `/var/lib/ttbox/models`（`cp -a -n`，不覆盖不删）。呼叫点 `:491`。

不迁的三类：配置（旧 `default.json` 里的客户调参不搬到 `/etc/ttbox/config.d/`，fhs_init 只在 `10-device.json` 不存在时放**模板**，`deploy/config/10-device.json` ⇒ 得到模板值而非客户旧值）、HID 包（旧 `/opt/ttbox/hid` 无迁移点）、授权状态（旧授权文件无迁移点）。

脚本自己声明"不需要迁移状态机"的理由是"存量设备 = 0"（`:12`）——这是**假设不是保证**。一旦有存量板，这三类就是静默丢数据。

### 刻意豁免（不要当缺口去"修"）

### 否掉的误报（两条）

1. **"`release_install.sh` 的 TAR_EXCLUDES 少了 5 项 ⇒ 会把 api_v1.py / framework_api.py 装进去"** —— 不成立。`release_install.sh:225` 是 `tar -C "$payload" "${TAR_EXCLUDES[@]}" -cf - .`，打的是传入的 payload 目录，不是仓库根；payload 由 fhs_init 白名单产出，那 5 个文件根本不在里面。真实问题降级为 D07（校验缺口 + 维护风险），不是漏货。
2. **"有 systemd unit 引用了装不上的东西"** —— 不成立。7 个 unit 的 unit 级引用（`User`/`Group`=ttbox、`RuntimeDirectory`/`StateDirectory`、各 `ExecStart` 二进制、`WorkingDirectory`、`/etc/ttbox/config.d`、预编译 `usb-proxy`）全部能被安装流程满足。D04/D05 那两条是**出货代码硬编码**，不是 unit 直引。

### 容易误判成"安装/卸载脚本"的三个（不是）

- `scripts/a9_pkg_install.sh` / `a9_pkg_rollback_demo.sh`：HID Package 生命周期演示，硬编码 `/home/ubuntu/ttbox2/...` 开发沙箱路径，操作对象是 `ttbox-hid-pkg` 的 registry。与设备安装无关，且不进出货包。
- `scripts/ttbox-web-reset-credentials.sh`：只删 `/etc/ttbox/web_credentials.json` 并重启 web，是**忘记密码恢复**，不是出厂重置。
- `scripts/legacy/ttbox_m2_license_accept_v1_authflow.py` 的 `--restore-valid`：验收脚本的测试态还原，不是产品备份恢复能力。

### 孤儿脚本（附带的清理项，不是缺口）

`scripts/` 下无任何调用方的：10 个 `a9_*.sh`、`ttbox_git_mode_check.sh`、`ttbox_ensure_selftest.sh`、`ttbox_release_selftest.sh`（build_release 只在结尾 echo 提示）、`ttbox_m207_accept.py`、`ttbox_m207_b21_expire.py`、`ttbox_m2xx_console_accept.py`、`scripts/legacy/*`、`wifi_manager.py`。这些多为一次性手工调试脚本，留着无妨。

两处值得单独说：
- `deploy/inject_edid.sh` **完全没被使用**，功能已被 `scripts/edid/edid_apply.sh` 取代，处于孤儿状态。
