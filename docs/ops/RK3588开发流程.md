# RK3588 开发流程（强制）

> 本文是 TTBOX RK3588 的固定开发流程。任何开发、修改、修复、测试都必须按此执行，不允许跳过或更换顺序。

## 一、强制顺序

```text
本机开发
→ 本机测试
→ 本机修 Bug
→ 本机全部测试通过
→ 交叉编译
→ 打包
→ 上板
→ 最终真机验证
```

## 二、硬性规则

1. 开发阶段不上板。
2. 所有能在 Windows 本机发现的问题，全部本机解决。
3. 每次修改后本机编译、测试、回归。
4. Worker1 写代码、测试、修 Bug。
5. Worker2 审查代码、测试结果、主动找 Bug。
6. Worker1 / Worker2 持续互相检查，直到本机测试全部通过。
7. 本机没有通过，不允许交叉编译，不允许上板。
8. 本机全部通过后，才允许：
   - ARM64 交叉编译
   - 生成 Release 包
   - 校验产物
   - 部署到 `192.168.0.104`
   - 账号 `root/root`
9. 上板只做最终硬件验证，不再进行开发式反复修改。
10. 最终重点验证：
    - HDMI/V4L2
    - RGA
    - RKNN/NPU
    - 推理
    - 模型切换
    - 鼠标移动
    - 热键
    - HID
    - 服务重启
    - 长时间运行
11. 上板发现问题，记录下来，回本机统一修复，再次完整本机测试通过后，再重新交叉编译上板。
12. 禁止在板端直接修改源码。
13. 禁止假 PASS，必须有真实测试证据。

## 三、本机通过标准

- Windows 本机 C++ 编译零错误。
- `ctest` 全部通过，保存真实输出。
- Python / Web / 平台测试全部通过（如适用）。
- 每次修改后重新执行全量回归，不能只跑增量测试。
- 测试结果存档，作为交叉编译和上板的前置证据。

## 四、交叉编译与上板门槛

1. 仅在本机全 PASS 后开始交叉编译。
2. 顺序固定：交叉编译 → Release 打包 → 产物校验 → 部署。
3. 产物校验至少包含：目标架构、文件哈希、文件清单、服务配置一致性。
4. 上板账号固定为 `192.168.0.104` / `root` / `root`。
5. 板端只做最终硬件验证，不在板端修改任何源码。

## 五、上板验证记录模板

| 验证项 | 预期 | 实际 | 结果 | 证据 |
|---|---|---|---|---|
| HDMI/V4L2 | `/dev/video0` 可采集 |  | PASS/FAIL | 命令输出/日志 |
| RGA | RGA 缩放/裁剪正常 |  | PASS/FAIL | 日志/帧数据 |
| RKNN/NPU | NPU 推理正常 |  | PASS/FAIL | 日志/帧率 |
| 推理 | 检测框数量与置信度正常 |  | PASS/FAIL | 日志/截图 |
| 模型切换 | 切换后生效且稳定 |  | PASS/FAIL | 日志/回读配置 |
| 鼠标移动 | 输出后端产生移动 |  | PASS/FAIL | 日志/usbproxy 状态 |
| 热键 | 门控符合配置 |  | PASS/FAIL | 日志/输入测试 |
| HID | HID 包/透传正常 |  | PASS/FAIL | 日志/设备状态 |
| 服务重启 | 全部服务恢复 |  | PASS/FAIL | systemctl 状态 |
| 长时间运行 | 无异常退出/卡死/泄漏 |  | PASS/FAIL | 运行时长/监控记录 |

上板发现问题时，按规则 11 处理：记录问题 → 回本机统一修复 → 本机全量测试通过 → 重新交叉编译 → 重新上板。
