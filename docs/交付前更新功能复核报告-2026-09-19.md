## 三、发现的问题

### P0-1：发布树属主污染——定案 §2.2 的安全论证被击穿

**板上坐实**（只读测试）：`sudo -u ttbox test -w /opt/ttbox/current/scripts/ttbox_ota_updater.py` → **可写**。
`find /opt/ttbox/releases -user ttbox` → **61 个文件**，含 root 身份执行的更新器本体。

**根因链**：OTA 包在 WSL 打包，默认用户 uid=1000 → 更新器用 Python `tarfile.extract()` 解包
（updater:297/302，**未做属主归一**），root 解包时按包内 uid 还原 → 板上 uid 1000 = ttbox →
staging 文件 ttbox 属主。浇筑段 `tar --no-same-owner`（release_install:226，`366fcf1` 补的）能让**浇筑后**是 root，
但：① 现板上这棵 1.4.6 是该修复**之前**浇的，61 个 ttbox 属主文件原样留着；
② **窗口期仍在**：解包 → 浇筑之间，staging 里的文件（bin/ttbox_core_main 等）是 ttbox 可写的，
web 进程在窗口内篡改 staging，浇筑后即以 root 运行——**写任务文件通道"只能装签名包"的论证就此失效**。

**修复方案**（三件一起）：
1. `normalize_staging_perms()`（updater）加 `os.chown(p, 0, 0)`——该函数已遍历全树，顺手归一属主；
2. `release_verify` 加断言：**发布树内不得存在 ttbox 属主或 ttbox 可写文件**（fail-closed）；
3. 板端整治：`chown -R root:root /opt/ttbox/releases`（现存 61 个文件），整治后复跑 doctor。

### P1-1：任务文件写入竞态

web 以最终名 `job-%d.json` 直接 `open()` 写（web:1903-1907），path 单元感知到文件存在即触发，
`json.dump` 未写完时更新器可能读到半截 JSON → `job_invalid` 归档 failed。
窗口很小但真实。**修复**：先写 `.tmp` 后缀再 `os.rename()` 原子改名（rename 后才匹配 glob）。

### 中（三条）

1. **`ttbox.sh` install 鸡生蛋**（:27）：`cmd_install` 先 `require_current`，全新板 current 必不存在即 die——与"首次安装"语义矛盾。首装应转发 `fhs_init`。
2. **备份缺 current 软链与 `/opt/ttbox/state`**（ttbox_backup.sh:19）：三处备份恢复到新板后 current 无着落，ensure/doctor 全红。应补记软链目标 + state 目录。
3. **`ttbox_ota_sign.py` 默认私钥目录仍是仓库内 `tools/ota/.testkeys/`**（:148/:165）：与登记的 `C:\ttbox-ota-keys` 不符，照默认操作会把私钥写进仓库目录（gitignore 能挡住入库，但违背 O12"本机固定目录"）。默认值应改为登记路径。

### 低（记录在案，随手修）

- `process_jobs` 用类而非实例调 `_write_status`（updater:421），功能对但不规范
- `ttbox_uninstall.sh:27` plan() 打印字面花括号，复制不展开（实际代码 :46 正确）
- `ttbox_restore.sh:37/47` `systemctl stop/start || true` 吞失败（有 doctor 兜底）
- web:1845 注释变量名误写 `TTBOX_OTA_SERVER_URL`（实为 `OTA_SERVER_URL`，ttbox.sh 侧同名同值由 doctor 比对）
- `ttbox_ota_sign.py` 允许空口令生成明文私钥（:66-77），仅提示不建议
- `test_verify.py` case_downgrade_rejected 末尾 `web_src.write_text("pass")` 死代码
- `ttbox.sh:54` 查询带契约外的 `?current=` 参数（假服务器忽略，无害；契约可顺手登记）
